# FreshBliss system description

How the shop is built and run: hosting, settings and secrets, the layers that protect money and data, the Excel bridge, and the storefront. The design brief (colours, type, copy rules) is `README.md`; the launch checklist is `docs/GO_LIVE.md`; how to run it on your own machine is `docs/DEVELOPING.md`; what is done and what comes next is `docs/FEATURE_AUDIT.md` and `docs/ROADMAP.md`.

Last checked against the code: 6 October 2026. When a change alters anything below, update this file in the same commit.

## Chapter 5: API & Deployment Infrastructure

### 5.1 Cloud Environment Variables & Secrets
To ensure strict security, FreshBliss isolates public configuration from private server operations.
*   **Next.js Frontend (Vercel):** Only public values, all prefixed `NEXT_PUBLIC_`: the Firebase web config (`FIREBASE_API_KEY`, `AUTH_DOMAIN`, `PROJECT_ID`, `APP_ID`, and optionally `STORAGE_BUCKET`, `MESSAGING_SENDER_ID`), `RECAPTCHA_SITE_KEY` (the public App Check key) and `SITE_URL` (the shop's address, for canonical links, the sitemap and share cards). There is no Razorpay variable in Vercel: the public Razorpay key id is served to the browser by the `createCheckout` Cloud Function with each checkout quote. `web/.env.example` lists them; `docs/GO_LIVE.md` section 4 says where each one is set.
*   **Firebase Backend (Cloud Functions):** Four private values live in Google Cloud Secret Manager (set with `firebase functions:secrets:set`): `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `EXCEL_AWS_SECRET_ACCESS_KEY` and `ERASURE_HASH_KEY` (the key that turns a customer's id into the anonymous hash left behind by data erasure). Non-secret settings live in `functions/.env.<alias>`: `RAZORPAY_KEY_ID`, `RAZORPAY_MODE`, `EXCEL_S3_BUCKET`, `EXCEL_S3_KEY`, `EXCEL_AWS_REGION`, `EXCEL_AWS_ACCESS_KEY_ID`, and three switches, `ENFORCE_APP_CHECK` (off by default), `AUTO_REFUNDS` (on by default) and `LOW_STOCK_THRESHOLD` (default 5). `RAZORPAY_MODE` (`test` or `live`) must agree with the key id prefix (`rzp_test_` / `rzp_live_`) or checkout refuses to run, so real money can only be taken by a deliberate switch. `functions/.env.example` lists every setting.

### 5.2 Hosting & Edge Deployment
*   **Frontend Distribution:** Deployed on Vercel, as a Next.js **Pages Router** app (`web/`, Root Directory `web`). The catalogue pages (`/`, `/products`, `/products/[slug]`) are built on the server from the active products (`lib/serverCatalog.js` reads Firestore over its REST interface) and rebuilt in the background every 10 to 60 seconds, so search engines and slow phones get a full page at once; if Firestore cannot be reached the page is built empty and retried after 10 seconds, and the browser's live listener fills it. Everything personal (cart, checkout, account, orders, admin, login) is rendered in the browser. Hashed assets under `/_next/static/` are cached as immutable, and `web/vercel.json` deliberately sets no `Cache-Control` override.
*   **Live data:** `lib/catalog.js` keeps one Firestore listener (`onSnapshot`, active products only) that takes over from the server-built page, so prices, stock and "Out of stock" change without a reload.
*   **Backend Execution:** Cloud Functions (v2) are deployed strictly to the `asia-south1` (Mumbai) region next to the Firestore database, for the primary Bengaluru delivery market. `setGlobalOptions` makes that the default, and `tests/regions.test.js` fails if any function is elsewhere.
*   **Installable:** a web manifest and icons (`web/public/`) let a phone "Add to Home screen". There is deliberately no service worker, so nothing is cached offline and a stale price or order status can never be shown.

### 5.3 Protection of money and data
*   **The server decides.** The browser can only read public data, read its own orders, and write its own cart, wishlist and feedback. `createCheckout` re-prices the saved cart from `products`, `deliveryZones` and `promoCodes`, then creates the Razorpay order; `verifyPayment` (HMAC signature) and `razorpayWebhook` (`order.paid` only) both end in one idempotent Firestore transaction (`functions/shared/payments.js`) that takes stock, counts promo use and creates the order exactly once. An order that cannot be fulfilled (sold out mid-payment, promo limit reached) is cancelled and refunded automatically.
*   **Firestore rules** (`firebase/firestore.rules`) are default-deny and covered by emulator tests. Closed to every browser (only the functions write them): `checkouts`, `promoCodes`, `rateLimits`, and, by the default-deny rule, `paymentEvents`, `refunds`, `excelSync` and `erasureLog`.
*   **App Check** (reCAPTCHA v3) makes the public functions refuse scripts that are not the real web app. It is behind `ENFORCE_APP_CHECK`; the deployment preflight refuses a live deploy with it off.
*   **Rate limits** (`shared/rateLimit.js`): every public function counts calls per signed-in user and per network address (kept only as a hash); a failed counter lets the request through and logs an error rather than block a customer.
*   **Content Security Policy and security headers** are enforced from `web/vercel.json` (Razorpay, Google sign-in and reCAPTCHA are the only outside script and frame sources), with `noindex` on private routes. It is still unproven against live traffic: `docs/GO_LIVE.md` section 5.4 is the walk-through.
*   **Refunds** (`shared/refunds.js`, `autoRefund`, `processRefund`): the amount is reserved in Firestore first and the Razorpay call carries an idempotency key, so a retry cannot refund twice. Each refund is a document in `refunds/`; refund webhooks move the order to `REFUNDED` or `PARTIALLY_REFUNDED`.
*   **Sign-in and privacy:** Google, Microsoft and phone sign-in, with the guest's orders carried over (`claimGuestOrders`). The DPDP consent tick-box is on `/login`; "Delete my data" on `/account` runs `requestDataErasure`, which anonymises personal fields but keeps the books (`shared/erasure.js`).

### 5.4 Operations and monitoring
*   `npm run setup-alerts` (in `firebase/`) creates an email channel and two Cloud Monitoring policies: any function `ERROR`, and **Low stock** (`functions/lowStock.js` logs a warning when stock first falls to the threshold and again at zero). Details: `docs/GO_LIVE.md` section 11.1.
*   The staff dashboard is `/admin/orders` (custom claim `staff: true`): move an order along, cancel, retry or check a refund, retry the Excel sync, download the orders workbook.

### 5.5 Checks before code reaches production
*   `.github/workflows/ci.yml` runs on every pull request and every push to `main`: in `web/` the tests, lint and a production build (with made-up public values); in `firebase/` the full emulator suite (rules, payments, orders, unit, Excel) with Java.
*   `main` is what Vercel publishes, so changes reach it only through a pull request with CI green. The money-path rehearsal (`npm run rehearsal` in `firebase/`) and `docs/GO_LIVE.md` section 9 are run by hand.

## Chapter 6: The Phased Execution Roadmap

The FreshBliss codebase was engineered in phases to ensure stability and prevent architectural overlap. Phases 1 to 6 built the shop; phases 7 to 9 hardened it and made it launch-ready. What comes next is `docs/ROADMAP.md`.

### Phase 1: Frontend Foundation & Design System
*   **Objective:** Establish the visual brand and component library.
*   **Execution:** Built the Tailwind CSS design system using the brand tokens (`tokens.json` at the repository root, turned into `web/styles/tokens.css` by `web/scripts/build-tokens.mjs`; Cream `#f5f1e9`, Deep Green `#173f2a`, Gold `#c99b3b`). Developed static UI screens with mock data, including the Ramadan theme toggle system and Framer Motion animations.

### Phase 2: Database Schema & Security Architecture
*   **Objective:** Lock down the data layer before connecting the UI.
*   **Execution:** Defined the Firestore schemas (`products`, `orders`, `carts`, `deliveryZones`). Wrote the `firestore.rules` enforcing a default-deny policy and public read-only access for products. Validated by automated security-rule tests using the Firebase Local Emulator Suite.

### Phase 3: The Checkout Loop & Payment Integration
*   **Objective:** Handle money securely and prevent inventory race conditions.
*   **Execution:** Built the Razorpay integration. Engineered the `createCheckout` and `verifyPayment` Cloud Functions. Implemented the server-side webhook to act as a fallback, utilizing a strict Firestore Transaction to ensure stock is decremented exactly once.

### Phase 4: Real-Time Fulfillment & Logistics
*   **Objective:** Enable live tracking for customers and operational control for staff.
*   **Execution:** Built the customer-facing `/orders/[id]` page using `onSnapshot` for instant UI updates. Secured the `/admin/orders` operations dashboard using a Firebase Custom Claim (`staff: true`), including a dedicated "Needs Refund" queue for stock-out cancellations.

### Phase 5: Business Operations Sync (The Excel Bridge)
*   **Objective:** Give the business a reporting spreadsheet without putting load on, or risk to, the live database. Firestore stays the source of truth; the spreadsheet is a copy, and a failed copy never affects an order.
*   **Storage (AWS S3):** The workbook is one file, `orders/orders.xlsx`, in a private S3 bucket (Block Public Access on, versioning on so a damaged file can be restored, default encryption). The functions reach it with a dedicated IAM user whose policy allows only `s3:GetObject` and `s3:PutObject` on that one object plus `s3:ListBucket` on the bucket (without it S3 reports a missing file as "access denied"). Settings: `EXCEL_S3_BUCKET`, `EXCEL_S3_KEY`, `EXCEL_AWS_REGION`, `EXCEL_AWS_ACCESS_KEY_ID`; the secret key is the Secret Manager secret `EXCEL_AWS_SECRET_ACCESS_KEY`. Setup: `firebase/docs/AWS_SETUP.md`.
*   **The `excelSync` trigger (order created):** Turns each new order into one 19-column row (columns A to P are written once, including the delivery slot in P; the three "live" columns Q to S are Payment status, Order status and Last updated). The `exceljs` library edits the workbook in memory. S3 cannot edit part of a file, so every change is read, change, write back; the write-back is **conditional on the file's ETag** (`If-Match`; `If-None-Match: *` for the very first file). If another function saved in between, S3 answers 412, and the change is redone from the new version (up to 30 times, with a short random pause), so concurrent orders never overwrite each other. Adding a row first looks for the order's ID in column A and does nothing if it is already there, so a retry after a lost reply can never create a duplicate row.
*   **The `excelSyncUpdate` trigger (order changed):** Runs only when `status` or `paymentStatus` changed. It finds the order's row by its ID (never by a stored row number, because staff may sort the sheet), rewrites only columns Q to S, and does not save at all if they already show the right values. It re-reads the order after writing and writes again if it changed meanwhile, so overlapping updates always end on the latest status. An update that arrives before its row exists waits up to 30 seconds for it. A row that staff deleted on purpose is not added back; it is recorded as `ROW_MISSING`.
*   **Resilience:** One ledger document per order (`excelSync/{orderId}`, server-only) records `PENDING`, `DONE` or `FAILED`, and what the sheet was last told. Busy or unreachable AWS is retried 4 times (1s, 2s, 4s, or the `Retry-After` header, capped at 15s); wrong credentials, missing permission, a missing bucket or a damaged file fail at once with a plain-English hint in the log. A staff **Retry Excel sync** button (`retryExcelSync`) re-sends whatever failed and is safe to press at any time.
*   **Formula sanitization:** Customer text is untrusted. Any text cell that begins with `=`, `+`, `-` or `@` (or a tab or carriage return) is stored with a leading `'`, so it can never run as a spreadsheet formula, even if the sheet is later exported to CSV or pasted elsewhere. Money is written as real numbers so the sheet can add it up. In this file the apostrophe is visible at the start of the cell; that is expected.
*   **Staff download (`getOrdersDownloadUrl`):** A staff-only callable (it checks the `staff` custom claim) used by the **Download orders sheet** button on `/admin/orders`. It asks S3 for one byte first (so a missing file is reported immediately), then signs a **read-only link that expires after 15 minutes**, for that one object only, with `Content-Disposition: attachment` and a dated file name. Signing happens on the server with `@aws-sdk/s3-request-presigner`; the link carries the access key id and a signature, never the secret. Every download is logged with the staff member's uid. Staff open a downloaded copy and never upload an edited file over the live one.
*   **Known limits:** Each change rewrites the whole file (fine for tens of thousands of rows; archive old orders beyond that). Charts and pivot tables in the live file are lost on the next save, so reporting is done in a downloaded copy. Only status changes are copied after creation, and orders created before the sync was configured are not back-filled. A workbook made before the slot column existed has the old headers and is refused (`bad-headers`) until it is moved aside.

### Phase 6: Storefront Completion (Home, Product, Checkout, Account, Receipt)
*   **Objective:** Finish the customer journey on top of the existing backend without moving any money or stock logic into the browser.
*   **Shared live catalogue:** `lib/catalog.js` keeps a single Firestore listener (`onSnapshot`, active products only) that feeds every page and the cart; the listener runs only while a component is on screen. Optional product fields the owner may add in Firestore: `images` (up to 4), `origin`, `calories` (text), `keyBenefits` (up to 6 phrases), `nutritionNote`, `packaging`. The first three feed the "Harvest & Health" row on the product page (`components/HarvestHealth.js`, `lib/harvest.js`); a missing field is left out of the page, never invented. The premium range (Exotics and Immunity categories, each with its own home-page tab) is seeded with placeholder facts to verify before launch.
*   **Product (`/products/[slug]`):** photo gallery with thumbnails, size selector (price follows the size), accordion (ingredients, nutrition if known, packaging), a quantity stepper that stops at the stock left (stock is shared across sizes, 20 per line), and a delivery estimate from the visitor's pincode.
*   **Checkout (`/checkout`):** delivery details, a delivery slot (as soon as possible, or a window today or tomorrow with a 90-minute lead, in IST; the rule is in `functions/shared/slots.js` and `web/lib/slots.js`, kept equal by a test), a rider tip (0, 10, 20 or 30), a promo code and an itemised summary. The pincode is matched against the live `deliveryZones` with the same rule the server uses (lowest `priority` first, first regex that matches) for an instant fee, or an "Outside delivery area" alert. The **total is the server's**: a read-only callable, `previewCheckout`, prices the cart with the very same functions as `createCheckout` but charges nothing, saves nothing and touches no stock. Promo codes exist only on the server (with optional global and per-account use limits), so a code is "applied" only once the server accepts it. The cart page only holds the cart.
*   **Account (`/account`):** the customer's own orders, live and newest first, from a query the security rules allow (`uid` equals the signed-in user), backed by a composite index (`uid`, `createdAt` descending), with a Reorder button that pushes each past line back through the cart's own stock and limit rules. It also holds the sign-in card and the "Delete my data" section.
*   **Order page and receipt (`/orders/[id]`):** live status, the delivery code while out for delivery, and a Cancel button until the order is packed (`cancelMyOrder` always restocks and starts the refund). A `<dialog>` modal holds a printable receipt (order number, date, itemised lines, discount, delivery, tip, total, slot, a masked payment reference); `window.print()` plus `@media print` rules leave only the receipt on the page. It prints the amounts charged and no tax line, because orders store no tax breakdown.
*   **Premium UX layer:** a global slide-out cart (`CartDrawer`, a native `<dialog>`, so focus is trapped, Esc closes it and focus returns to the cart button), toast notifications (`ToastProvider`: a polite live region), skeleton screens that copy the layout of the real content for every loading state, a sticky header, a command palette, and a phone tab bar. Provider order in `_app.js` is Toast, Auth, Cart drawer, Command palette, Cart, Wishlist; the error boundary wraps only the page.
*   **Storytelling and cross-selling:** a "Farm to table" trust story, an "Add something with it" row on each product page (`lib/related.js`), and a footer with a newsletter box (UI only, and it says so), quick links, the live delivery zones, and hours or contact details only when the shop has filled them in. Policy pages (`/privacy`, `/terms`, `/refunds`, `/faq`) state only what the systems do; the words live in `web/content/`.
*   **Local checkout without Razorpay:** when the storefront is talking to the emulators (never true in a production build), the checkout page skips Razorpay: an emulator-only function, `createMockOrder`, writes the order with the Admin SDK (priced by the same code as the real checkout; status `PREPARING`, `paymentStatus` `PAID_MOCK`; no stock taken), and the visitor lands on the live tracking page. `PAID_MOCK` is never `PAID`, so `cancelOrder` refuses a test order and it can never enter the refund queue. The function is kept out of production three ways: it is exported only when `FUNCTIONS_EMULATOR` is `true`, it refuses to run outside the emulator, and the page only calls it in emulator mode.
*   **Visual system:** Playfair Display for every `h1` to `h3`, and Plus Jakarta Sans for all other text, both loaded with `next/font` (self-hosted at build time, so no request to Google and no CSP change). Tailwind v4 has no separate config file: the theme lives in CSS (`styles/globals.css`) and the generated `styles/tokens.css`. Colours come from the design tokens, so the light, dark and high-contrast themes keep working (the page currently ships the light theme only; a chooser is on the roadmap); only the hero, which is always dark, uses fixed values. All motion is `motion-safe:`.
*   **Quality gates:** `npm test` and `npx eslint .` in `web/` (pure logic such as zones, pricing, sorting, slots, plus copy and parity tests), `npm test` in `firebase/` (rules, payments, orders, previews, regions, refunds, erasure, Excel sync), `npm run rehearsal` (a 35-check run of the whole money path against the emulators), a production `next build`, and the CI workflow that runs all but the rehearsal.

### Phase 7: Real accounts, refunds and compliance
*   **Sign-in:** `/login` with Google, Microsoft and phone; a guest becomes the account (same uid) or, if that identity already has one, `claimGuestOrders` moves their orders. The checkout asks to sign in and offers "Continue as guest".
*   **Refunds:** `autoRefund` sends a full refund to Razorpay when an order is cancelled with a refund pending; `processRefund` lets staff retry, check or refund part of a delivered order. Payment capture must stay on Automatic in the Razorpay dashboard (`docs/GO_LIVE.md` section 6): the code only creates an order once money is captured.
*   **Promo limits:** per-code global and per-account limits are counted inside the payment transaction, so racing buyers cannot exceed them.
*   **Customer rights:** Terms and Cancellation & Refunds pages, a consent line at checkout, DPDP consent on `/login`, and erasure from `/account` (`shared/erasure.js`, `shared/excelErasure.js`). Receipts and the footer show the FSSAI licence once `content/business.js` has one.

### Phase 8: Hardening and operations
*   **Abuse protection:** App Check and per-user and per-address rate limits (section 5.3).
*   **Alerts:** error and low-stock emails (section 5.4); the Excel sheet gained a delivery-slot column.
*   **Search and sharing:** canonical and Open Graph tags, JSON-LD, `sitemap.xml` and `robots.txt` (`lib/seo.js`).

### Phase 9: Frontend pass
*   A longer, richer home page (pincode check, Shop by category, How it works, "Everything a good fruit order needs", a closing call to action), shop sorting and an "In stock only" switch, a back-to-top button, a restructured footer and a helpful 404; the product page's Add to Cart overlap on desktop and the empty server-built pages in `next dev` were fixed. Details: `docs/FEATURE_AUDIT.md`, "Frontend pass".

### What is not built yet
Real photos and logo, business details, customer feedback after delivery, a theme chooser, email or SMS to customers, a working newsletter, a browser end-to-end test, and the tax breakdown. Each is planned in `docs/ROADMAP.md`. Nothing has yet run against real Firebase, Razorpay, AWS or Vercel accounts.
